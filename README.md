# MAX — чат

Небольшой клиент MAX на React и TypeScript. Пользователь подключает свой инстанс GREEN-API, открывает чат по номеру телефона, отправляет текст и получает ответы. Интерфейс ориентирован на тёмную тему веб-версии MAX: список чатов слева, переписка справа. На телефоне эти области показываются по очереди.

## Запуск

Нужен Node.js 22 или новее.

```bash
npm ci
npm run dev
```

Открой адрес, который напечатает Vite, обычно `http://localhost:5173`.

```bash
npm test          # тесты API-клиента, очереди, состояния и сценария интерфейса
npm run typecheck # проверка TypeScript
npm run build    # готовое приложение в dist/
npm run preview  # локальный просмотр сборки
```

Не открывай `index.html` двойным кликом: приложению нужен HTTP-сервер. Готовую папку `dist` можно разместить на любом статическом хостинге. Backend и переменные окружения не нужны.

## Подключение GREEN-API

1. Создай инстанс **MAX** в [кабинете GREEN-API](https://console.greenapi.com/). Подключи к нему свой аккаунт MAX; состояние должно быть `authorized`. QR и 2FA обрабатываются в кабинете сервиса.
2. Скопируй **idInstance**, **apiTokenInstance** и **apiUrl** в форму приложения. `apiUrl` берётся из карточки инстанса, а не вычисляется по его ID.
3. Приложение проверит состояние и настройки. Если уведомления не настроены, предложит отдельную кнопку настройки. Она очищает `webhookUrl` и включает `incomingWebhook`, `outgoingWebhook`, `outgoingMessageWebhook`, `outgoingAPIMessageWebhook`, `stateWebhook`. Это делается только после нажатия пользователя, а не при каждом входе. Если ранее был настроен webhook другого сервиса, он перестанет получать уведомления.
4. После изменения настроек инстанс может перезапускаться до пяти минут. Нажми «Проверить подключение», когда он будет готов.
5. Создай чат по номеру с кодом `+7` или `+375`, отправь сообщение и ответь с другого аккаунта MAX.

Получение должно обслуживаться только одним клиентом: не запускай параллельно другой скрипт или вкладку с тем же инстансом. При наличии Web Locks браузер сам оставляет один потребитель очереди среди вкладок этого приложения на одном origin.

## Что реализовано

- Ввод и проверка данных GREEN-API; проверка состояния MAX.
- Создание личного чата по номеру через `CheckAccount`, повторное открытие известного номера без лишней проверки.
- Отправка текста через `SendMessage`, в том числе переносов строк и эмодзи. Лимит — 4000 UTF-16 единиц (`String.length`), это консервативно для эмодзи.
- Один последовательный цикл `ReceiveNotification → обработка → DeleteNotification`. Long polling — 25 секунд, запрос отменяется при выходе.
- Обычный текст, текст со ссылкой и текст ответа с цитированием. Ссылки отображаются как текст, HTML не исполняется.
- Исходящие сообщения из телефона/API, статусы `delivered`, `read`, ошибки `failed`, `noAccount`.
- Устранение дублей по паре `chatId + idMessage`, обработка статуса, пришедшего раньше ответа отправки.
- Отдельные черновики, сохранение текста при ошибке, индикаторы подключения, непрочитанные сообщения.
- Enter отправляет сообщение, Shift+Enter добавляет строку. Ввод через IME не вызывает случайную отправку.
- Автопрокрутка при новых сообщениях, если пользователь внизу; кнопка возврата вниз при чтении старой переписки.
- Адаптивный интерфейс, подписи кнопок, диалог с нативным фокусом и Escape.

## Решения и ограничения

**Ключи и история живут только в памяти вкладки.** Приложение не пишет их в localStorage, sessionStorage, URL страницы или логи. После обновления страницы нужны повторный вход и создание чатов. Уже подтверждённые уведомления не воспроизводятся: загрузка прежней истории не входит в ТЗ. Сообщения остаются в MAX. Не отправляй реальные ключи вместе с исходниками.

**Запросы идут напрямую в GREEN-API.** Хост назначения проверяется до первого запроса. Как у любого браузерного клиента, ключ виден владельцу вкладки в DevTools. Для отдельного публичного продукта нужен backend с авторизацией пользователей; здесь реализовано требование ТЗ о вводе собственных ключей. Если конкретный сервер GREEN-API блокирует CORS, приложение покажет сетевую ошибку. Реальное подключение к пользовательскому инстансу нужно проверить отдельно.

**Неопределённая отправка не повторяется автоматически.** При сетевом обрыве сервер мог принять сообщение. В таком случае текст остаётся в поле, а пузырёк предлагает проверить MAX перед повтором, чтобы не отправить дубликат. Не выполняется рискованное сопоставление сообщений только по тексту.

**Настройки не меняются незаметно.** `SetSettings` вызывается отдельной кнопкой только при необходимости. Проверка номера не использует `force`, чтобы не обходить кэш сервиса и не расходовать лишние проверки.

**Минимальный объём.** Нет вложений, звонков, групповых чатов, редактора профиля, поиска, базы данных, регистрации в самом приложении и имитации онлайн-статуса собеседника. Нет предзаполненных вымышленных переписок или деморежима. Группы, вложения и посторонние события обрабатываются как неподдерживаемые и подтверждаются, чтобы не задерживать следующие текстовые сообщения. Если известное текстовое событие повреждено, приём останавливается без его удаления.

**Очередь и повторные запросы.** При временных ошибках получение повторяется с задержкой до 30 секунд. Пока подтверждение не получено, новый Receive не запускается. Ошибки доступа и некорректные ответы останавливают цикл и показывают «Проверить». Если DELETE сообщает, что событие уже удалено, приложение просит проверить второго потребителя очереди.

## Структура

- `src/components` — экран подключения, список чатов, переписка и форма нового чата.
- `src/hooks/useChat.ts` — связывает API, состояние чатов и жизненный цикл запросов.
- `src/lib/greenApi.ts` — HTTP-запросы и безопасные тексты ошибок.
- `src/lib/notifications.ts` — перевод уведомлений GREEN-API в события приложения.
- `src/lib/chatState.ts` — состояние переписок, дедупликация, слияние статусов.
- `src/lib/polling.ts` — последовательная очередь, повторы и отмена.
- `src/lib/validation.ts` — номера телефонов и данные подключения.
- `tests/app.test.tsx` — сценарий интерфейса с подменённой сетью.
- `TASK.md` — требования и зафиксированные решения из обсуждения.

Состояния достаточно мало для React-хуков. Redux, роутер и универсальные абстракции здесь не нужны. Из runtime-зависимостей — React, React DOM и иконки lucide-react. Стили написаны обычным CSS.

## Проверка перед сдачей

Автотесты проверяют поведение приложения на моделируемых ответах API. Они не подтверждают доступность конкретного инстанса, CORS или реальную доставку в MAX. Для последней проверки:

1. Подключить авторизованный инстанс и открыть чат второго аккаунта.
2. Отправить текст из сайта, убедиться, что он появился в MAX.
3. Ответить из MAX обычным текстом, затем текстом со ссылкой и цитатой.
4. Проверить, что ответы попали в тот же чат и не продублировались.
5. Временно отключить сеть, проверить восстановление получения и сохранение черновика при ошибке.
6. Открыть второй чат и проверить сохранность черновиков при переключении.

На бесплатном тарифе есть ограничения по чатам и проверкам номеров. Актуальные условия стоит проверить в кабинете; приложение не перебирает номера и не выполняет массовых отправок.
